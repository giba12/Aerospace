A walkthrough of the project · C++17 and Python

How far can you trust a sensor that is always a little wrong?

sensor-sim simulates an object moving along a line, reads its position through a noisy sensor, and recovers the true position, and the speed the sensor never measures, using only those readings. It then checks its own answer against the truth it kept hidden.

What it does

Truth is simulated first, so the exact answer is always known. A seeded sensor adds random error to a reading every half second. A Kalman filter turns the readings into a running estimate with its own error bars. A recorder writes every step to a CSV, and a Python script scores the estimate against the truth.

What it sets out to show

That an estimator can be built the way safety-minded teams build software: every requirement has an ID, every test names the requirement it checks, a script fails the build when one loses its test, and each claim is checked against data the filter was never tuned on. The page below lets you see both halves.

Educational simulation. It is not flight software and has not been qualified for any use. It does not model a real sensor, real vehicle dynamics, or operational sensor fusion (SYS-006).

The idea in one picture

One reading, one update

The filter keeps two things: a best guess and how unsure it is. Between readings it moves the guess forward and lets the doubt grow. When a reading arrives it blends the reading into the guess. The more doubt the filter has compared with the sensor's noise, the harder it leans on the reading. The result is narrower than either input.

This shows the position half of one step. The real filter keeps position and velocity together, so each reading also corrects its estimate of speed, which is how it finds a quantity the sensor never reports.

Evidence

How do we know the filter is right?

"It looked good on one run" proves little, so the filter is checked three independent ways. The third matters most: the 50 seeds below were never used to choose a setting or a threshold.

Check 1 · Reference vector

A fixed worked example

Unit tests compare the first predict and update with the reference vector in the project baseline (VV-EST-01), which came from an independent prototype (EST-001).

Check 2 · Independent oracle

Same filter, different code

kalman_oracle.py rebuilds the estimates from the readings alone, in 60-digit decimal arithmetic, never importing the C++. A test compares the two.

Check 3 · Held-out seeds

50 runs it was never tuned on

Seeds 1001 to 1050 were kept apart from tuning. The filter must beat the raw readings on every one, and its error bars must be honest.

Reproduce it

One command to see the same results

The script builds the simulator, runs the reference scenario, prints the metrics and the independent cross-check, and writes the CSV, the metrics file and the plot this page was built from.

git clone https://github.com/giba12/Aerospace
cd Aerospace
./run.sh              # build, run, analyze, cross-check
./run.sh --test       # also build and run the whole test suite

Needs Linux, a C++ compiler, CMake, Ninja and Python 3.12, or just Docker or Podman. The container build runs the whole test suite before it will produce an image.

What is automated on every push

  • Two compilersGCC 13 and Clang 18, with warnings as errors.
  • SanitizersAddressSanitizer and UndefinedBehaviorSanitizer run the whole suite.
  • Traceability gateThe build fails if a Must requirement loses its passing test.
  • CoverageAbout 94 % of library lines, measured with gcov; reported, never used as a gate.
  • Time budgetThe full suite must finish inside 30 seconds (NFR-006).
  • Clean-room containerBuilds from a fresh copy, tests inside the image, runs the scenario.
  • Claims are testedA test fails if the README quotes a number that a fresh run no longer produces.
  • DeterministicThe same seed and settings give a byte-identical CSV on the same build.

Everything on this page is computed from files in the repository: the recorded run in out/run.csv, the seed table in docs/VALIDATION.md, and the requirement and test links found by scanning docs/ and tests/. tools/build_demo.py regenerates the page.
