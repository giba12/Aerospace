# Claim-to-evidence table (VAL-07)

> This is a small educational simulation, not flight software, and it makes no claim of flight qualification, operational fidelity or real sensor fusion (SYS-006).

**What this is.** Baseline validation item VAL-07 asks: *are the claims true?* Its acceptance criterion is that every
README claim has a row here, that no claim is unsupported, and that the SYS-006 statement is present. Each row below
quotes a claim from [README.md](../README.md) word for word and points at what supports it.

**It is checked, not just written.** `tests/python/test_evidence_table.py` fails the build if a quoted claim is no
longer in the README, if a README paragraph or bullet has no row, if a referenced test, file, CI job or requirement does
not exist, or if a row claims a kind of evidence it does not cite. A row can still be *wrong* about what a test proves; the
**Caveat** column says where the evidence is weaker than the claim.

## How to read the Strength column

| Code | Meaning |
|---|---|
| **T** | An automated test that runs on every build checks it. |
| **C** | A CI job or step checks it on every push. |
| **R** | A recorded measurement or observation. It is reproducible with the stated command but is not re-run automatically, so it can go stale. |
| **I** | Inspection: the file itself is the evidence (a configuration line, a design choice). A test may guard it against drift. |
| **X** | An external fact (a standard, a mathematical identity) rather than something this repository establishes. |

Evidence items are written `test:path::name`, `file:path`, `req:ID`, `ci:job` or `ci:job/step`, and `obs:` for a
recorded observation. A claim that could not be supported was changed in the README, not given a flattering row; see
"What this review changed" at the end.

## What this repository does not support

These are claims someone might be tempted to make about the project. Nothing here backs them:

- **That the owner can derive or explain the Kalman filter.** The hand-calculation worksheet
  ([docs/M3_WORKSHEET.md](M3_WORKSHEET.md)) was skipped, and the validation item for understanding (VAL-06, the
  explain-back questions) has not been done. The tests show the filter is *correct*, not that anyone *understands* it.
  The baseline names this as the project's largest risk.
- **That the filter works on real data, on a real sensor, or when the truth accelerates.** All validation is simulated
  and the filter fails under acceleration (C-77).
- **Anything about flight qualification, operational fidelity or real sensor fusion** (C-01, C-02).
- **That the results hold with another standard library or on macOS or Windows.** Only GCC 13 and Clang 18 on Linux
  with libstdc++ have been run.
- **That the oracle tolerance is part of the approved baseline.** CR-26 is still proposed.
- **A licence.** None has been chosen.
